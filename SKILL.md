# PR review

You are reviewing a PR that was most likely generated by Claude Code. Assume the diff looks clean and CI is green. Your job is to find what a clean-looking AI diff hides: tests that prove nothing, changes outside the stated intent, reinvented helpers, silent changes to shared libs that other apps depend on, and config changes nobody asked for.

Rules that apply to every section:
- A finding without evidence (file:line, test output, caller list, existing function path) is reported as "unverified" and cannot be a Blocker or Major.
- Be direct. No praise, no summary of what the PR does well.
- Never modify files on the PR branch. Read, run, report.

## 1. Fetch and frame

1. Input is a PR URL and its source branch. Run:
   - `git fetch origin main <branch>`
   - `git diff --name-status origin/main...origin/<branch>`
   - `git diff origin/main...origin/<branch>`
   - `git log --oneline origin/main..origin/<branch>`
   If `gh` is available, also run `gh pr view <url>` for the title and description. If not, use the branch name and commit messages.
2. If the PR has no description, record a Major finding: "No PR description. Intent below is inferred and may be wrong."
3. Write the intent statement: two sentences, what this PR appears to do and why. Every pass judges the diff against this statement. Put it at the top of the report.
4. Group changed files into: app code, shared libs, tests, config/infra (Helm, k8s manifests, CI workflows, Dockerfiles, env files, pyproject.toml, uv.lock, package.json, lockfiles), other.
   Shared libs exist only if the repo has packages imported by more than one app (uv workspace, a `libs/` or `packages/` folder, or similar). For a single app or a monorepo of independent apps, there is no shared libs group; say so explicitly.
   Read the repo's CLAUDE.md if present: it may define the test command, app locations, and repo-specific rules. Prefer it over the defaults below.
5. Extract the list of changed public symbols: functions, classes, methods, constants whose signature, return shape, or behavior changed. Section 3b needs this.

## 2. Passes

Spawn one subagent per pass, in parallel. Each subagent receives only: its pass instructions below, the full diff, the intent statement, and the file groups. It does not see the other passes. Each returns findings as a list of `{severity, file, line, title, evidence, explanation}`.

### 2a Scope drift
Judge every changed file against the intent statement.
- Flag any file or hunk that does not serve the intent: unrelated refactors, renames, reformatting, "while I was here" fixes.
- Flag deletions of code, tests, or config the intent does not explain.
- Formatting-only changes in files the PR legitimately touches are Nits, not drift.
Output: one finding per drifting file. Major if it changes behavior, Minor if not.

### 2b Test integrity
Read only. Do not run tests here.
For every test file touched, and every changed function with no touched test:
- Tests deleted, marked skip/xfail, or with loosened assertions (asserts removed, exact values replaced with `is not None` or truthiness, exception checks broadened, tolerances widened): Blocker.
- Tests where the code under test is mocked out so the test passes even if the implementation is broken: Major. Cite the mock and the function it hides.
- Changed functions in app code or shared libs with no test exercising the new behavior: Major.
- Any change to a numeric or pricing computation with no test asserting the new value: Blocker.
Output: findings with file:line and the exact assertion or mock.

### 2c Reuse
Search before you claim. Never report a duplicate without the path and name of the existing function.
- For every new helper, utility, model, or client added by the PR, search the whole repo for an existing implementation of the same thing (`rg` on the function name, key identifiers, and docstring terms). Search shared libs first if they exist.
- If an equivalent exists in a shared lib: Blocker. Cite the existing path.
- If an equivalent exists elsewhere in the same app: Major.
- If the PR copies code from a shared lib into an app instead of importing it: Blocker.
Output: new symbol, existing symbol path, severity.

### 2d Behavior trace
Pick the single most important code path the PR changes: from the entry point (API route, Prefect task, CLI command, React action) to the final effect (MongoDB write, response payload, computed value).
- Walk it step by step, reading the actual code, not just the diff.
- Describe the behavior before the PR and after the PR in plain language.
- Flag any point where the new behavior is logically wrong, handles an error path incorrectly, changes a default, or produces a different value than before without the intent explaining it. A logical bug is a Blocker.
- Flag unhandled error paths, swallowed exceptions, and silent fallbacks as Major.
Output: the path traced, before/after summary, findings.

### 2e Config, infra, security
Review every file in the config/infra group plus anything touching secrets, auth, external endpoints, or environment.
- Helm values, k8s manifests, CI workflows, Dockerfiles, env vars, or dependency changes (pyproject.toml, uv.lock) that are not the point of the PR: Blocker.
- Dependency added: check it is actually used in the diff. Unused dependency: Major.
- Hardcoded secrets, tokens, internal URLs, or credentials: Blocker.
- Changes to logging that could leak trade or client data: Major.
- Changes to timeouts, retries, batch sizes, or resource limits with no justification in the intent: Major.
Output: findings with file:line.

## 3. Evidence

Run these after the passes, in the main agent.

### 3a Run the suite on the branch
- `git checkout <branch>` (stash local changes first if any), install dependencies (`uv sync` for Python, `npm ci` for JS, or whatever CLAUDE.md says), then run the test suite for every app and lib touched by the PR: `uv run pytest <path>` per group by default. Use the repo's own test command if CLAUDE.md or the CI config defines one.
- Capture the summary line (passed/failed/skipped counts) and the full output of any failure.
- Suite fails: Blocker. Skipped count higher than on main: Major, list the skips.
- Return to the previous branch when done.

### 3b Blast radius
Only run if a shared libs group exists. Otherwise write "Blast radius: not applicable, no shared packages" in the evidence run and skip this step. In a monorepo of independent apps, still `rg` for cross-app imports of changed symbols; if there are none, say so.
For every changed public symbol from step 1.5 that lives in a shared lib:
- `rg -n "<symbol>" --glob '!<changed package path>'` across the monorepo to list every caller, grouped by app.
- For each caller: was it updated in this PR? If the signature or return shape changed and a caller was not updated: Blocker. Cite the caller file:line.
- Run the test suite for every affected app that the PR did not already test in 3a. Report results the same way.
Output: table of symbol, callers by app, updated yes/no, tests run yes/no, result.

### 3c Mutation testing (only when invoked with `--mutate`, or when the PR touches pricing or numeric code)
- Python only. If `mutmut` is not installed, report "Mutation: mutmut not available" and skip. Otherwise run `uv run mutmut run --paths-to-mutate <changed files>` with the relevant test paths.
- Report the survived mutant count and list survivors. A survived mutant in a changed function means the tests do not protect it: Major.

## 4. Merge and report

Merge all findings from sections 2 and 3:
- Deduplicate findings that point at the same file:line and cause; keep the highest severity.
- Apply the evidence rule: any finding whose evidence field is empty is moved to "Unverified".
- Verdict:
  - REQUEST CHANGES if any Blocker.
  - NEEDS HUMAN CALL if no Blocker but 3 or more Majors, or the behavior trace could not reach a conclusion.
  - APPROVE otherwise.

Severity definitions (do not reinterpret):
- Blocker: suite fails; test deleted, weakened, or skipped; shared lib signature or return shape changed with a caller not updated; Helm/k8s/CI/env/dependency change that is not the point of the PR; numeric or pricing change without a test proving the new value; logical bug in the traced path; duplicate of something that already exists in a shared lib; hardcoded secret.
- Major: would cause a bug or a support ticket but not a prod incident; unhandled error path; duplicated logic within an app; mocked-out code under test; missing PR description; unused dependency; unjustified timeout/retry/limit change.
- Minor: code quality a human reviewer would flag: naming, structure, dead code, non-behavioral drift.
- Nit: style and formatting.

Write the report to `reviews/<pr-number>-<branch>.md` (create `reviews/` if missing; it is gitignored). Also print it.

Report format:
